```
┌──────────────────────────────────────────────────────────────┐

┌───────────────────────────▼──────────────────────────────────┐

│  • 心理情绪评估 + 阈值预警（FR-009~011）                        │
```

## 2. 职责划分（需求 10.3）

| 环节 | 负责方 |
|---|---|
| 意图分类（判断用户要干嘛） | Dify question-classifier（结合对话历史） |
| 知识库问答（政策/FAQ/公司） | Dify 检索 + LLM，不经过后端 |
| 画像研判推荐课程 | 后端规则引擎（确定性匹配度） |
| 心理情绪评估 + 预警存储 | 后端（关键词兜底 + 写预警 + 通知班主任） |
| 活动报名 / CRM / 成绩 / 日报 / 请假 | 后端读写 SQLite |
| 结果润色成中文话术 | Dify LLM 节点 |
| 上下文管理 | 后端持久化 conversation_id + Dify memory 窗口 |

## 3. 关键设计决策

1. **对话经后端代理而非前端直连 Dify**：API Key 不暴露给浏览器（需求 12.3）；
   无需改 Dify nginx CORS；统一沉淀对话记录与情绪标签；Dify 故障时后端就地降级。
2. **降级链路（需求 11.1/13.2）**：Dify 不可用 → 学生侧走情绪/请假/成绩/工单本地规则，
   员工侧走 NL2SQL，客服侧走画像规则 + 本地 FAQ 检索（knowledge/faq.json 与 Dify 知识库同源）。
3. **自由文本安全传输**：Dify 中所有含用户原文的请求体先经 Python 代码节点 json.dumps，
   杜绝引号/换行破坏 JSON；LLM 抽取的画像 JSON 解析失败时后端正则兜底。
4. **NL2SQL 为确定性解析 + 参数化 SQL**：白名单表、意图正则、实体识别不到明确提示不猜测，
   满足可解释、可复现、可追溯（G-06），同时避免 LLM 生成 SQL 的注入风险。
5. **权限模型**：sys_user.user_type（STUDENT/EMPLOYEE）+ employee_role（顾问/班主任/管理员）。
   学生仅本人数据；审批/预警/工单解决仅班主任与管理员；后台仅管理员；Dify 工具持 X-API-Key 全量放行。
6. **端口**：本机 8000 被既有项目占用，本系统用 8010（启动脚本/测试/DSL 已统一）。

## 4. 数据流示例

**心理预警**：学生聊天 → 后端代理 → Dify 分类为「情绪倾诉」→ code 构造请求 →
POST /api/student/emotion → 关键词/LLM 评估 90 分 → upsert 画像（历史≤50）→
写 student_psych_alert（teacher_id=班主任）→ Dify LLM 共情话术 +「已通知班主任」→
班主任后台「心理预警」可见并跟进/解除。

**项目推荐**：访客描述画像 → Dify 分类为「推荐」→ LLM 抽取结构化画像 JSON →
code 解析（失败兜底）→ POST /api/courses/recommend → 规则引擎匹配评分（93分）→
附 course_project 关键信息 → Dify LLM 组织推荐理由 + 引导留资。
