## 本次实际采用的接入方式（答辩可讲）

1. **导入工具集**：工具 → 自定义 → 创建自定义工具，粘贴 `tools_openapi.json`，
   授权方式选「请求头」，头部名称 `X-API-Key`，值为后端 `TOOL_API_KEY`（默认 xinxifang-tool-key-2026）
2. **导入应用**：工作室 → 导入 DSL → URL 方式（`http://host.docker.internal:8010/<yml>`，需临时把 yml 放入 backend 静态目录）
3. **关键坑（重要）**：DSL 头部 `version` 必须写当前 Dify 支持的版本（本机为 **0.5.0**）。
   若沿用旧版 `0.1.5`，导入管道会走 legacy 迁移，把工具节点的 `tool_parameters` 搬进
   `tool_configurations`，导致应用编排页崩溃（Cannot convert undefined or null to object）。
   工具节点 v2 格式三要素：`tool_parameters`（参数映射）、`tool_configurations: {}`、`tool_node_version: "2"`
4. **provider_id 必须是工具集 UUID**：运行时按 `ApiToolProvider.id`（UUID）精确查找，
   若填工具集名称会报 `invalid input syntax for type uuid`。本机 UUID 为
   `17402d99-abdd-4fe6-a062-72d14d31d0b3`（SQL：`SELECT id FROM tool_api_providers;`）
5. **应用落地方式**：先导入临时应用验证画布与知识库绑定无误，再把旧应用的草图画布替换为
   新画布并重新发布——旧应用身份与 API 密钥不变，前端 `.env` 零改动

## 回滚方式

- 三个旧应用每次发布都会生成带时间戳的版本行，回滚即在 Dify 应用「编排 → 发布历史」中还原，
  或删除最新一条已发布记录即可回到 HTTP 节点版本
- `tools_openapi.json` / 三个 `*_agent.yml` 已更新为最终版本，可随时重新导入
- `frontend/*.yml` 为临时静态副本（用于 URL 导入），可留可删

## 品牌替换踩坑记录（2026-11-21）

除代码/文档/SQL 文本替换外，以下运行侧问题需要单独处理，排查耗时最长，记录备查：

1. **凭据密钥字段名**：`tool_api_providers.credentials_str` 为 AES 密文，改值必须走
   `ApiToolManageService.update_api_tool_provider`（容器内 Python + test_request_context）。
   credentials 字典的字段名必须为 **`api_key_value`**（存密钥值）+ `api_key_header`（存头部名），
   写成 `api_key` 会在运行时报 `Missing api_key_value`。
2. **改凭据后必清缓存**：api 容器有内存/Redis 缓存，改完需
   `docker exec docker-redis-1 redis-cli FLUSHALL` + `docker restart docker-api-1`。
3. **发布指针**：直接 INSERT workflows 行后必须同步更新 `apps.workflow_id` 指向新版本，
   否则运行时仍用旧发布版本（表现：改了 graph 但行为不变）。
4. **工具节点 provider_id 格式**：见上文第 4 条，必须 UUID，占位符/名称都不行。
5. **品牌替换范围**：除仓库文件外，还需同步改——
   Dify 库（apps.name / workflows.graph 全版本 / datasets.name / messages、conversations 历史文）、
   SQLite 业务库行数据（如 event_lecture.location 活动地址、sys_user 电话）、
   以及 Dify 知识库内已索引的文档内容（需在 Dify 知识库重新上传 `knowledge/*.md`）。
